# 실제 코드를 설명하기 위한 학습·면접 가이드

기준: 2026-09-23 작업 트리. AI가 코드를 생성했더라도 런타임에서 왜 이 순서로 실행되는지 직접 설명하는 것이 목표다. 모든 파일의 작성 주체를 추정하지 않는다. 아래 대안은 비교 학습용이며 패키지 변경 권고나 현재 사용 기술을 뜻하지 않는다. 실습은 **별도 합성 DB·가짜 공급자·모의 블로그**에서 수행하고 실제 글을 발행하지 않는다.

## 1. 반드시 설명할 핵심: TypeScript와 런타임 입력 검증

1. **무엇인가**: TypeScript는 실행 전 변수/함수의 데이터 형태를 검사한다. HTTP·DB JSON은 실행 중 들어오므로 타입 선언만으로 안전해지지 않는다.
2. **이 프로젝트에서의 목적**: 원고·블록·사진·작업 결과의 계약을 공유하고, 잘못된 입력을 저장/발행 전에 거절한다.
3. **위치**: [model.ts](../src/lib/model.ts)의 `Draft`, `DraftBlock`, `Job`; [store.ts](../src/lib/store.ts)의 `validateDraft`; [blocks.ts](../src/lib/blocks.ts)의 `validateBlocks`; [ai/content.ts](../src/services/ai/content.ts)의 `parseOutput`.
4. **순서**: JSON 파싱→unknown/object 검사→필드 타입/길이→버전/ID/참조 검사→정규화→저장. 블록 원고는 markdown/images를 서버가 다시 계산한다.
5. **장단점**: 계약이 명확하고 리팩터링 오류를 줄인다. 수동 검증 코드가 타입과 따로 존재해 둘이 달라질 수 있다.
6. **대안**: JavaScript+검증 함수, Zod 같은 schema 검증. 이 프로젝트에 Zod가 설치되어 있다고 설명하면 안 된다.
7. **주의**: `as Draft`는 실제 데이터 검사가 아니다. `Job.state`의 string과 Codex의 any는 보호가 약한 경계다. schemaVersion과 원고 version은 서로 다른 개념이다.
8. **연습**: `validateDraft`에 사진 ID 중복/없는 cover/알 수 없는 schemaVersion을 넣어 어떤 단계에서 거절되는지 설명한다. 앱 코드는 바꾸지 않고 별도 테스트에서 출력 대신 성공/거절만 기록한다.
9. **질문**: “TypeScript를 쓰는데 왜 validateDraft가 필요합니까?”
10. **답변**: “컴파일러는 제 코드 내부 계약을 검사하지만 브라우저나 저장된 JSON이 그 타입인지 보증하지 않습니다. 이 앱은 서버에서 길이·버전·사진 참조를 검사한 후 저장해 잘못된 데이터가 전송까지 넘어가지 않도록 합니다.”

## 2. 반드시 설명할 핵심: React 상태와 Next.js 로컬 API

1. **무엇인가**: React는 state 변경을 화면으로 표현하고 Next는 페이지와 HTTP 요청 처리 진입점을 제공한다.
2. **목적**: 편집 상태와 저장된 서버 상태를 구분하면서 같은 프로젝트 안에서 로컬 파일/DB를 안전하게 다룬다.
3. **위치**: [page.tsx](../src/app/page.tsx) `Home/api/refresh`, 패널 컴포넌트, [api/app/route.ts](../src/app/api/app/route.ts) `GET/POST`, [layout.tsx](../src/app/layout.tsx).
4. **순서**: controlled input→draft state/dirty→POST save→서버 검증/DB→새 버전 state. 미리보기는 300ms 지연 후 POST, 작업 상태는 2.5초 GET.
5. **장단점**: 브라우저로 폼·미리보기를 쉽게 제공한다. 전체 state 조회와 한 페이지의 많은 책임은 데이터가 늘면 비용/복잡도를 높인다.
6. **대안**: 정적 UI+별도 Express 서버, 데스크톱 wrapper, 상태 라이브러리. 지금 규모에서 Redux를 추가해야만 하는 것은 아니다.
7. **주의**: Next Route Handler는 서버 코드다. 쿠키/파일 경로를 client component에 넣지 않는다. 현재 API는 action 기반이며 엄격한 REST로 포장하지 않는다. 폴링은 WebSocket 실시간 push가 아니다.
8. **연습**: `save` 버튼부터 `saveDraft`까지 호출 지도를 그린다. mock fetch의 응답 순서를 뒤집어 오래된 응답이 setState에 도달하는 상황을 재현하고 sequence/abort 해법을 설명한다.
9. **질문**: “AI 요청을 POST 안에서 끝까지 처리하지 않은 이유는 무엇인가요?”
10. **답변**: “긴 생성/브라우저 동작을 화면 요청의 수명과 분리하려고 DB에 작업을 넣고 worker가 처리하게 했습니다. 화면은 상태를 조회합니다. 단, 자료 URL fetch는 아직 요청 안에서 처리하고, 전체 상태 폴링은 개선 대상입니다.”

## 3. 반드시 설명할 핵심: SQLite 트랜잭션·버전·파일 일관성

1. **무엇인가**: SQLite는 파일 기반 관계형 DB다. 트랜잭션은 관련 DB 변경을 함께 성공하거나 되돌리고, WAL은 읽기/쓰기 운영 방식이다.
2. **목적**: 별도 DB 서버 없이 원고와 작업을 재시작 후 복구하고 여러 창의 편집 덮어쓰기를 막는다.
3. **위치**: [store.ts](../src/lib/store.ts) `openStore/transaction/saveDraft`, [ai-store.ts](../src/lib/ai-store.ts) `tx/apply`, [photo-analysis.ts](../src/lib/photo-analysis.ts) `apply`.
4. **순서**: BEGIN IMMEDIATE→현재 원고 version 조회→입력 version 비교→사진 존재 확인→현재본/새 버전 저장→COMMIT. 오류면 ROLLBACK.
5. **장단점**: 설치가 간단하고 로컬 영속성이 좋다. DatabaseSync의 큰 조회는 Node event loop를 막을 수 있고 JSON 필드 검색·대용량 동시 처리에는 제약이 있다.
6. **대안**: JSON 파일은 단순하지만 트랜잭션/쿼리가 약하다. PostgreSQL은 서버형 다중 사용자에 유리하지만 지금보다 운영 부담이 크다. ORM은 사용하지 않는다.
7. **주의**: DB commit이 외부 PNG 저장이나 티스토리 저장까지 원자적으로 만들지 않는다. 사진 적용은 `saveDraft` 후 `put`이 분리되어 실패 불일치를 이번에 확인했다. nested BEGIN을 넣으면 해결되지 않는다.
8. **연습**: 두 창이 같은 v1을 읽은 뒤 A가 v2를 저장하면 B의 v1 저장이 왜 거절되는지 합성 DB로 확인한다. 사진 작업 기록 실패 시 원고도 v1로 남아야 한다는 회귀 기준을 작성한다.
9. **질문**: “원고 저장과 AI 적용의 일관성을 어떻게 보장합니까?”
10. **답변**: “입력 버전과 현재 버전을 비교하고 현재본·이력을 같은 트랜잭션에서 저장합니다. AI apply도 같은 방식입니다. 다만 사진 분석 apply는 두 DB 저장이 분리된 결함을 발견했으며 아직 수정 전입니다.”

## 4. 반드시 설명할 핵심: 작업 큐·중복키·임대·복구

1. **무엇인가**: 큐는 처리할 작업을 영속적으로 기록한다. 중복키는 같은 요청을 구분하고 임대는 만료 시간이 있는 worker 소유권이다.
2. **목적**: 중복 클릭·프로세스 중단·외부 저장 응답 유실에서 기존 원고와 게시 결과를 추적한다.
3. **위치**: [store.ts](../src/lib/store.ts) `enqueue/acquire/claim/heartbeat/verify`, [worker.ts](../scripts/worker.ts), `tests/recovery.test.ts`.
4. **순서**: snapshot+dedupe 저장→임대 소유 worker claim→단계 기록→저장 요청 경계를 먼저 DB 기록→외부 저장→URL 확보→읽기 검증→succeeded. 중단 시 unknown/attention으로 남긴다.
5. **장단점**: 요청 재전송을 억제하고 재시작 후 추적할 수 있다. DB와 티스토리가 별도이므로 저장 직후 응답 유실을 완전히 없앨 수 없다.
6. **대안**: 메모리 큐는 재시작에 취약하다. Redis/BullMQ 등 별도 큐는 규모에 따라 유용하지만 단일 PC에는 인프라 부담이 있다.
7. **주의**: 임대는 15초·3초 갱신, 외부 작업을 DB 잠금 안에서 실행하지 않는다. exactly-once가 아니다. candidatePostUrl은 검사 전 결과 주소가 아니다. 사용자 미발행 확인도 자동 증명은 아니다.
8. **연습**: 입력 중, 사진 업로드 중, 저장 직전, 저장 직후, URL 확보 후 각각 프로세스가 종료되면 어떤 상태/다음 행동이 필요한지 표를 만든다.
9. **질문**: “API 타임아웃이면 재시도하면 되지 않나요?”
10. **답변**: “외부 저장이 이미 성공했을 수 있어 자동 재시도하면 중복 글이 생길 수 있습니다. 이 앱은 저장 요청 뒤 결과가 불명확하면 unknown으로 남기고 기존 URL/관리 목록을 읽어 확인합니다. 외부 정확히 한 번 저장을 보장한다고 말하지 않습니다.”

## 5. 반드시 설명할 핵심: AI 공급자·프롬프트·구조화 출력

1. **무엇인가**: App Server와 stdio 메시지를 주고받는 adapter다. 요청 ID가 있는 응답과 작업 진행 알림을 구분하고 구조화된 생성 결과를 검증한다.
2. **목적**: 기존 사용자 선택인 ChatGPT 로그인 경로에서 초안/문체/사진 설명을 만들고 결과가 임의 실행이나 자동 발행으로 이어지지 않게 한다.
3. **위치**: [codex.ts](../src/services/ai/codex.ts) `CodexClient.start/call/status/complete`, [content.ts](../src/services/ai/content.ts) `prompt/parseOutput`, `AiRunner.tick`.
4. **순서**: 앱 전용 저장소→initialize→계정/모델/한도→thread/start→프롬프트+localImage+outputSchema→turn/start→알림/usage 수집→출력 검증→job 저장→사용자 적용.
5. **장단점**: 출처·문체·사진과 구조 계약을 함께 관리한다. 공급자 프로토콜/모델 응답 변화에 영향받고 JSON이 유효해도 사실성은 보장되지 않는다.
6. **대안**: API 키 기반 유료 공급자, 로컬 모델, 수동 결과 import. 현재는 이런 공급자를 구현하지 않았고 자동 비용 전환도 없다.
7. **주의**: 모델명은 계정 목록에서 선택한다. `WritingProvider`가 있어도 runner가 구체 analyze/photos 메서드에 의존해 완전히 교체 가능하지는 않다. 토큰 사용량은 청구 금액이 아니다. 프롬프트 지시만으로 인젝션을 완전히 막을 수 없다.
8. **연습**: 가짜 provider가 누락 사진 ID/다른 블록 순서/늦은 결과를 반환하게 하고 parse/apply가 어떻게 거절하는지 확인한다. 악성 지시가 들어 있는 합성 참고문을 도구 실행 없이 데이터로 처리하는 계약을 설명한다.
9. **질문**: “AI가 만든 글의 정확성과 안전성을 어떻게 검증했습니까?”
10. **답변**: “JSON·길이·블록/사진 ID·버전은 코드로 검사하고 참고 자료와 미확인 사항을 보존합니다. 사실성·경험·저작권은 사용자 검토가 필요합니다. 도구 실행은 비활성화하고 서버 요청도 거절하며, 생성과 발행은 별도 동작입니다.”

## 6. 반드시 설명할 핵심: Playwright와 외부 UI 계약

1. **무엇인가**: 실제 브라우저의 locator/iframe/file chooser를 제어하는 자동화 라이브러리다.
2. **목적**: 전용 Chrome의 사용자 로그인 상태로 티스토리 편집기에 텍스트·사진·비공개 설정을 입력한다.
3. **위치**: [tistory/probe.ts](../src/services/tistory/probe.ts) `TistoryProbe`, [publisher.ts](../src/services/tistory/publisher.ts) `connect/categories/publish/verify`.
4. **순서**: 관리 화면 로그인 확인→빈/같은 미첨부 원고인지 검사→HTML→기본모드→사진 순차 업로드→위치/대표/비공개 확인→저장→재편집/게시글 확인.
5. **장단점**: 사람이 쓰는 UI와 같은 경로를 검증할 수 있다. UI/스킨 변경과 로그인·CAPTCHA·사진 검토에 취약하고 서버 API 수준 안정성을 약속하기 어렵다.
6. **대안**: 지원되는 공식 게시 API가 있을 때 API adapter, 수동 복사/내보내기. 현재 코드를 공식 API 호출로 설명하지 않는다.
7. **주의**: 임의 sleep만으로 성공을 판단하지 않는다. 사진 개수·크기·식별자·순서를 검사한다. known dialog만 처리하고 다른 원고를 덮지 않는다. 실제 비로그인 접근 검사는 인수 스크립트에 있으며 매 일반 verify에 포함되는 것은 아니다.
8. **연습**: mock 티스토리 HTML에서 사진 순서/카테고리/공개 범위를 바꿔 verify가 실패하는 이유를 추적한다. 사진 업로드를 Promise.all로 바꾸면 왜 순서를 깨뜨릴 수 있는지 설명한다.
9. **질문**: “성공을 버튼 클릭으로 판단하나요?”
10. **답변**: “클릭만으로 완료 처리하지 않습니다. 글 주소를 확보하고 본문·사진·카테고리·비공개 표시를 읽어 확인합니다. 사진 처리 지연이나 스킨 불일치는 확인 대기로 두며, 한 계정에서의 인수를 모든 환경 성공으로 일반화하지 않습니다.”

## 7. 반드시 설명할 핵심: 로컬 보안·HTML/파일 검증

1. **무엇인가**: 인증/권한, CSRF, XSS, 입력 검증은 서로 다른 문제를 다룬다. 로컬 앱도 외부 페이지가 보내는 요청과 위험한 콘텐츠를 제한해야 한다.
2. **목적**: 단일 사용자 PC의 원고/세션을 외부 요청과 게시 HTML의 실행 가능한 입력에서 보호한다.
3. **위치**: [security.ts](../src/lib/security.ts) `checkRequest`, [content.ts](../src/lib/content.ts) `renderMarkdown/escapeHtml`, [assets.ts](../src/lib/assets.ts), run.mjs 제어서버.
4. **순서**: loopback binding→Host/Origin/Sec-Fetch-Site→mutation 헤더→byte 상한→필드 검증→HTML 정제/실제 이미지 디코딩→DB/파일 저장.
5. **장단점**: 코드 경계가 명시적이고 사진 메타데이터 제거를 제공한다. 같은 PC의 악성 프로세스나 로컬 파일 권한을 대신 보호하지 않는다.
6. **대안**: 외부 서비스용 로그인 세션·tenant 권한, OS credential store. 이는 추가 설계이며 현재 구현에 있다고 말하지 않는다.
7. **주의**: `local-web`은 공개 문자열이므로 사용자 인증 키가 아니다. Git 제외는 암호화가 아니다. 내부 Codex 로그에도 토큰이 남아 있으므로 `.local` 폴더 공유가 위험하다.
8. **연습**: 합성 Request로 다른 Origin/Host/헤더 누락을 검증하고 sanitize-html이 script·unsafe href·remote image를 제거하는지 확인한다. 실제 쿠키 값을 출력하는 연습은 하지 않는다.
9. **질문**: “127.0.0.1로 제한했으니 완전히 안전한가요?”
10. **답변**: “외부 네트워크 직접 접근을 줄이지만 같은 OS 사용자의 프로세스 접근까지 막지는 않습니다. Origin/헤더 검사는 웹 요청 경계를 보완하며 사용자 인증은 아닙니다. 외부 공개는 별도 인증/권한 설계가 필요합니다.”

## 8. 보조 핵심: 이미지 처리·해시·캐시

1. **무엇인가**: Sharp는 이미지 bytes를 읽고 변환한다. SHA-256 기반 캐시는 같은 입력 조건의 결과를 찾는 식별 수단이다.
2. **목적**: 잘못된 사진을 거절하고 원본 파일 경로/EXIF를 게시 흐름과 분리하며 작은 썸네일과 기존 AI 결과를 재사용한다.
3. **위치**: `assets.importImage/thumbnail`, `photoCacheKey`, `photoAnalysisStore.enqueue/finish`.
4. **순서**: 파일 크기/MIME→픽셀 제한 decode→rotate/PNG→UUID 파일/해시→thumbnail→사진 분석 시 모델·메모·group·프롬프트 버전 키→cache hit/miss.
5. **장단점**: 변경 조건을 구분해 재사용하고 UI 이미지 크기를 줄인다. PNG 변환이 항상 용량 감소는 아니며 고해상도 처리 메모리 부담이 있다.
6. **대안**: 원본 보관+파생 파일, 별도 이미지 서비스, DB blob. 현재는 로컬 PNG 파일+메타데이터 DB 방식이다.
7. **주의**: content hash는 암호화·권한 검증이 아니다. 파일이 같아도 모델/메모가 다르면 결과가 달라야 한다. 사진 캐시의 실 AI 인수는 아직 미검증이다.
8. **연습**: 같은 합성 사진에서 note/model/group을 하나씩 변경해 캐시 키가 바뀌는지 확인한다. input bytes와 PNG bytes·RSS를 측정해 압축 크기와 처리 메모리 차이를 본다.
9. **질문**: “왜 파일명으로 캐시하지 않았나요?”
10. **답변**: “이름이 같아도 bytes가 다를 수 있고 동일 사진도 요청 조건이 바뀌면 분석이 달라집니다. 이 앱은 이미지 내용 해시와 모델·메모·묶음·프롬프트 버전을 결합합니다.”

## 9. 보조 핵심: Markdown·DOM 추출·출처

1. **무엇인가**: marked는 Markdown을 HTML로 바꾸고 Cheerio는 HTML에서 필요한 본문을 선택한다. sanitize-html은 허용 태그/속성만 남긴다.
2. **목적**: 편집하기 쉬운 원고와 게시 미리보기, 대표 글/참고 자료의 정제된 본문을 제공한다.
3. **위치**: `content.renderMarkdown`, `references.extractReference/fetchReference`, `style/import.extractArticle/importPost`.
4. **순서**: URL 제한→타임아웃/본문 크기 제한 fetch→nav/script 제외→본문 추출→method/official/checkedAt 저장→생성 스냅샷으로 선택.
5. **장단점**: 소수 라이브러리로 텍스트/HTML을 다룬다. 사이트 구조에 민감하고 추출 성공이 사실 검증은 아니다.
6. **대안**: 수동 붙여넣기, 사이트별 parser, HTML 대신 AST 원고. 이미 붙여넣기 대안이 존재한다.
7. **주의**: Cheerio는 페이지 JS를 실행하지 않는다. `official:true`는 허용된 공식 호스트 표식이다. 외부 전문의 재배포 권한을 부여하지 않는다.
8. **연습**: nav/광고/script가 있는 합성 HTML에서 본문만 추출하고 코드/표가 Markdown 정제 후 유지되는지 확인한다.
9. **질문**: “출처 URL이 있으면 AI 답이 검증된 것인가요?”
10. **답변**: “아닙니다. 이 앱은 출처를 가져온 방법과 시점을 보존할 뿐 주장과 출처의 일치를 자동 증명하지 않습니다. 최종 사실 대조가 필요합니다.”

## 10. 보조 핵심: 백업·복원·Windows 실행 수명

1. **무엇인가**: 온라인 DB 백업과 파일 manifest는 일관된 스냅샷·무결성 확인을 제공한다. launcher는 웹/worker 프로세스 수명을 관리한다.
2. **목적**: 재시작/중단/복원 때 사용자 자료를 보존하고 잘못된 프로세스를 종료하지 않는다.
3. **위치**: `backup.createBackup/normalizeSnapshot/verifyBackup/restoreBackup`, `scripts/run.mjs`, `runtime-control.mjs`, `environment.mjs`.
4. **순서**: 활성 작업 확인→SQLite backup API→AI 연결/임대 초기화→사진 복사/hash→검증. 복원은 경로/손상 검사→안전 백업→교체→오류 시 이전 폴더 복귀. 시작은 환경→웹 instance health→worker ready다.
5. **장단점**: 인증을 백업에서 분리하고 실패 시 복구 지점을 남긴다. 사진/버전이 많아지면 IO/용량 부담이 커지고 타 PC/자동 업데이트는 별도다.
6. **대안**: 앱 정지 후 전체 복사, versioned 백업 도구, Windows 서비스/패키지 설치. 현재는 소스 폴더와 cmd 진입점이다.
7. **주의**: WAL 중 DB 파일만 복사하는 것은 안전한 스냅샷과 다르다. hash는 정상 파일과 일치 여부를 보지 악성 백업의 신뢰성을 인증하지 않는다. 코드 downgrade와 DB rollback은 다르다.
8. **연습**: 합성 사진 하나를 바꿔 verifyBackup이 거절하는지 확인한다. 빈 폴더 복원과 다른 파일이 있는 폴더의 거절을 비교한다.
9. **질문**: “왜 앱 폴더를 통째로 백업하지 않나요?”
10. **답변**: “인증·진단·빌드 캐시까지 섞이고 SQLite 쓰기 중 일관성 문제가 생길 수 있습니다. 필요한 DB 스냅샷과 참조 사진을 묶고 해시를 확인하며 로그인 상태는 복원 후 다시 확인합니다.”

## 11. 보조 핵심: 테스트·CI·성능 근거

1. **무엇인가**: 테스트는 특정 조건에서 기대 동작을 검증하고 CI는 그 검사를 자동 반복한다. 측정은 실제 병목 후보를 좁히는 방법이다.
2. **목적**: 버전/취소/복구 변경으로 과거 동작이 깨지지 않게 하고 구현 주장에 검증 범위를 붙인다.
3. **위치**: `tests/*.test.ts`, `scripts/web-writing-check.ts`, `check-build.mjs`, `.github/workflows/ci.yml`.
4. **순서**: 타입→32개 기존 테스트→빌드→개인 자료 추적 제외→격리 UI. CI 정의는 Windows 설치 검사도 포함한다. 실제 AI/발행은 별도 선택 인수다.
5. **장단점**: 계정/비용 없이 반복할 수 있다. 모의 UI/AI가 외부 서비스 변경과 실제 사실 품질을 보증하지 않는다.
6. **대안**: 다른 테스트 runner/coverage 도구/오류 수집 서비스. 현재 node:test에 불필요한 migration을 권하지 않는다.
7. **주의**: 32는 test 개수이며 assertion 수/커버리지 100%가 아니다. 이번 합성 GET 중앙값은 실제 사용자 체감 응답시간이나 개선율이 아니다. npm audit 0은 알려진 advisory 결과만 뜻한다.
8. **연습**: 같은 10/100/1000 원고 조건으로 응답 bytes와 handler time을 기록하고, future pagination 후 같은 조건에서 전후 비교 계획을 작성한다. UI 렌더 시간은 별도로 측정한다.
9. **질문**: “성능 개선 성과가 있나요?”
10. **답변**: “이번에는 전체 상태 조회가 커지는 것을 합성 데이터로 측정했습니다. 원고 1,000개에서 응답이 약 10.23MB였지만 아직 개선하지 않았으므로 개선율은 없습니다. 조회 범위를 나눈 뒤 같은 조건으로 비교할 계획입니다.”

## 12. 선택 학습: Docker 코드 실행

1. **정의**: 격리된 컨테이너 안에서 Python 코드를 실행하고 입력 예제의 실제 출력과 비교한다.
2. **목적**: AI/사용자 코드를 호스트에서 직접 실행하지 않기 위해서다.
3. **위치**: `src/services/code-check.ts`의 `dockerArgs/command/runCodeCheck`.
4. **순서**: 로컬 image 존재→네트워크 없음/읽기 전용/비루트/CPU·메모리·PID 제한 실행→출력 상한/timeout→container 정리→비교 결과 보관.
5. **장단점**: 호스트 실행보다 경계를 제공하나 Docker daemon·이미지 관리가 필요하고 완전한 보안 보증은 아니다.
6. **대안**: 실제 실행 없이 수동 trace, 별도 sandbox 서비스. 호스트 fallback은 현재 금지한다.
7. **주의**: 현재 실제 컨테이너 인수는 미완료이고 입력한 예제 통과가 정당성/온라인 저지 정답을 뜻하지 않는다.
8. **연습**: 먼저 dockerArgs에서 각 제한 인수의 역할을 설명하고 환경이 있을 때 합성 무한 루프·정상 출력·과다 출력의 결과를 별도 테스트한다.
9. **질문**: “코드가 정답임을 보장하나요?”
10. **답변**: “선택한 예제의 출력만 비교합니다. 알고리즘 정당성은 별도 검토 대상이고, 현재 Docker 실제 실행 검증도 남아 있어 실행 완료 기능으로 과장하지 않습니다.”

## 학습 순서와 완료 기준

1. 1~3장: 합성 원고 저장을 처음부터 다시 만들고 HTTP 입력 검증/버전 충돌을 설명한다.
2. 4~6장: 같은 요청·중단 시점·늦은 AI 결과를 표로 만들고 기존 회귀 테스트와 연결한다.
3. 7장: 실제 비밀값을 보지 않고도 로컬 경계·정제·인증 파일 공개 제외를 설명한다.
4. 8~11장: 사진 캐시·백업·CI·측정 수치를 직접 확인하고 한계를 말한다.
5. 12장과 Firebase/광고/결제/금융·모바일은 실제 지원 직무/추가 요구에 맞춰 선택한다. 이 프로젝트에 없는 기술을 이력서 스택에 넣지 않는다.

면접 전에는 “입력→검증→저장→외부 호출→오류→복구”를 파일을 보지 않고 3분 안에 설명해 본다. 설명이 막히는 코드가 있다면 작성자와 무관하게 학습 대상으로 남긴다. 성과 숫자·직접 역할·외부 성공 여부는 [분석 보고서](TECHNICAL_ANALYSIS_2026-09-23.md)의 근거 범위를 따른다.
