# 배포 준비 상태 점검

점검일: 2026-09-22 (Asia/Seoul) · 기준 커밋: `f460832`

후속 상태: 이 문서는 구현 전 점검 기록이다. 같은 날 R0.1에서 아래 1~3번 문제와 URL 없는 작업 복구를 수정하고 단위·빌드·로컬 UI/모의 게시글 검증을 완료했다. 실제 계정 재확인과 배포 인수는 남아 있다. 최신 결과는 [프로젝트 계획](../PROJECT_PLAN.md)의 R0.1 작업 기록을 따른다.

## 판단

현재는 **개인 PC에서 사용하는 티스토리 비공개 작성 도구의 핵심 MVP가 구현되고, 실제 계정 검증 이력이 있는 단계**다. 다른 사람에게 설치해서 쓰도록 제공할 배포판에는 복구·설치·업데이트 검증이 더 필요하다. 인터넷에 공개하는 다중 사용자 서비스는 현재 구조의 배포 옵션이 아니라 별도 설계가 필요한 범위다.

P0~P4 핵심 흐름과 R0 백업·복원 기반은 완료되었고, R1은 연동 가능성 판정까지 완료되었다. 전체 제품의 완료율을 숫자로 매기지는 않는다. R2~R7의 사진 편집·새 글 유형·플랫폼 확장·공개 발행·배포는 서로 작업량이 다른 미완료 단계다.

## 배포 전에 해결할 구체적인 문제

### 1. 저장 URL이 있어도 재시작 후 재확인할 수 없는 상태

- 근거: `src/lib/store.ts`의 `acquire()`는 단계가 `결과 확인`인 실행 중 작업을 재시작 때 `unknown`으로 바꾼다. `verify()`의 허용 상태에는 `unknown`이 없다. `src/app/page.tsx`도 그 상태에서는 재확인 버튼을 표시하지 않는다.
- 재현: 합성 발행 작업에 저장 URL 기록 → `running/결과 확인` → 임대 만료 후 새 실행기 획득 → `unknown`, URL 있음, `verify()` 거절.
- 영향: 새 글 중복 생성은 막지만, 이미 저장된 글을 앱에서 확인해 작업을 끝내는 경로가 막힌다. 실제 발행 후 중단에 대비한 배포 차단 항목이다.
- 필요한 수정: 저장 URL이 검증 가능한 경우 읽기 전용 재확인을 허용하고, URL이 없는 경우에는 관리 화면에서 확인한 글을 안전하게 연결하거나 결과를 정리하는 절차를 제공한다. 두 경우 모두 재발행 없이 복구되는지 검사한다.

### 2. 복원 보존 폴더의 이미지가 Git 제외 대상에서 빠짐

- 근거: `src/lib/backup.ts`는 데이터 폴더 옆에 `data.before-restore-*`, `data.failed-restore-*`, `.restore-*`를 만든다. `.gitignore`는 `data/`와 `backups/`만 폴더 단위로 제외한다.
- 확인: 각 복원 폴더 아래의 합성 `images/example.png` 경로는 `git check-ignore` 대상이 아니었다. SQLite 자체는 확장자 규칙으로 제외되지만 사진에는 해당 규칙이 없다.
- 영향: 복원 후 일괄 Git 추가 시 사용자 사진이 공개 저장소에 포함될 수 있다. 실제 유출을 발견한 것은 아니다.
- 필요한 수정: 복원 부산물을 모두 Git 제외 경로 아래에 두거나 해당 폴더 패턴을 제외하고 검증한다. 사용자 지정 데이터 경로에 대해서도 안내한다.

### 3. 새 PC의 빈 데이터 경로로 바로 복원하면 실패

- 근거: `restoreBackup()`은 대상의 기존 `app.sqlite`를 읽기 전용으로 먼저 연다.
- 재현: 정상 합성 백업을 기존 DB가 없는 폴더로 복원하면 DB 열기 오류가 발생한다.
- 영향: 기존 설치의 되돌리기는 가능하지만 신규 설치 후 바로 가져오는 복구 흐름은 완성되지 않았다. 먼저 앱을 실행해 DB를 초기화하는 우회는 가능하나 절차가 명확해야 한다.
- 필요한 수정: 신규 설치 가져오기와 기존 데이터 교체를 구분하고, 빈 경로·기존 데이터·손상된 백업의 동작을 검증한다.

### 4. 배포 실행 의존성과 초기 설정 정리

- `package.json`에서 `npm start`와 작업 실행기는 `tsx`를 사용하지만 `tsx`는 `devDependencies`에만 있다. 전체 `npm ci` 설치 경로와 달리 `--omit=dev` 배포에서는 실행 의존성이 빠진다. 런타임 의존성으로 옮기거나 실행기를 빌드 산출물로 제공할 필요가 있다. 실제 축소 설치 시험은 미실행이다.
- `src/lib/store.ts`의 초기 설정에는 개발자의 특정 블로그 주소가 들어 있다. 배포판은 최초 실행에서 사용자 블로그를 설정하게 하고 Node·Chrome·AI 실행 파일·포트 충돌을 진단해야 한다.
- 추적된 파일에서 CI 설정과 배포 라이선스 파일을 찾지 못했다. 다른 사람에게 공유할 범위에 맞게 사용 조건과 자동 검사를 정리해야 한다.

## 배포 목표에 따른 필요한 작업

### A. 개인용 Windows 로컬 앱 배포

가장 작은 배포 범위는 **티스토리·ChatGPT·기존 3개 글 유형·사용자 검토 후 비공개 저장**이다. 이 범위라면 여행 글·Gemini·네이버·예약을 모두 끝낼 필요는 없다.

1. 위 복구/데이터 보호 문제를 해결한다. 로그인 만료, 사진 업로드 중단, 저장 직후 응답 유실, 재시작 시 중복 없는 복구를 확인한다.
2. 설치·실행·종료·업데이트·이전 버전 복귀와 백업/복원을 하나의 사용자 흐름으로 정리한다. 인증 자료·진단 자료의 접근 권한, 마스킹, 보관·삭제 기준을 마련한다.
3. 다른 Windows PC와 다른 티스토리 계정에서 설치부터 생성·비공개 전송·재열기·복원을 끝까지 검사한다. 확인 대기 중인 기존 사진 문제도 같은 글에서 마무리한다.
4. CI에 타입·단위·빌드 검사를 넣고, 외부 계정/사용 한도를 쓰는 검사는 분리한다. 지원 버전과 호환성 재검사 절차를 정한다.
5. 공개 발행을 제품에 포함하려면 R6를 별도 완료한다. 새 공개 글 작성과 기존 비공개 글의 공개 전환을 구분하고, 지정한 시험 원고로 비로그인 표시와 중복 방지를 검증한다.

배포 인수 기준: 새 PC에서 자기 계정으로 설치·생성·전송·복원이 가능하고, 중단 후 글이 중복되지 않으며, 작업 결과를 사용자가 앱에서 정리할 수 있어야 한다.

### B. 인터넷에 접속해서 쓰는 웹 서비스

현재 `scripts/dev.ts`는 `127.0.0.1:3000`에만 바인딩하고 `src/lib/security.ts`는 해당 로컬 Host·Origin을 요구한다. 데이터와 로그인 프로필은 단일 사용자 저장소를 사용하며, 티스토리 자동화는 표시되는 Chrome과 장기 실행 작업 실행기를 전제로 한다.

따라서 호스팅 주소만 바꾸는 작업으로 완성되지 않는다. 사용자 인증·권한, 사용자별 DB/파일/브라우저 세션 격리, 인증 자료 보호, HTTPS와 서버용 요청 보호, 작업 실행 인프라, 저장소·백업·운영 모니터링, 로그인·CAPTCHA의 사용자 인계 경로가 필요하다. 기존 R7의 웹 UI + 사용자 PC 실행기 페어링도 대안이나, 페어링 인증과 연결 복구 설계가 추가된다.

## 제안하는 우선순위

- **배포가 우선이면:** 복구/데이터 보호 수정 → 설치·업데이트·새 PC 검증 → 제한된 로컬 베타. 공개 발행을 약속할 때만 R6를 필수로 추가한다.
- **원래 확장 제품이 우선이면:** 기존 R2 사진 블록 → R3 여행/정보/자유 글 → R5 네이버 제품화 → R6 공개 발행 → R7 운영 안정화 순서를 유지한다. 위 복구 문제는 그 전에 처리하는 편이 좋다.
- Docker 실제 실행은 PS 실행 검증을 제공할 때 필수이며 일반 글 배포 전체의 선행 조건은 아니다. Gemini와 예약도 초기 배포의 필수 조건으로 묶지 않는다.

이는 이번 분석의 제안이며, 기존 로드맵 변경이나 기능 구현 완료를 뜻하지 않는다. 기능 코드는 수정하지 않았다.
